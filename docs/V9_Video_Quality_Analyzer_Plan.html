01｜專案目標與界線

針對 V9 平台已錄製完成的 RAW、H.264、H.265、MJPG 影像檔案，離線批次分析 FPS、畫面凍結、綠色異常／殘影、模糊、色彩偏差與解碼異常，輸出可追溯的事件證據及測試報告。

4輸入格式
3解析度
12基本測試組合

範圍：離線檔案處理、CLI、批次報告與 Jenkins 整合。不包含：第一版即時 RTSP 分析、在 V9 SoC 上部署 CUDA、無參考資料即可保證所有主觀畫質判定準確。

核心原則：先用 CPU 建立正確、可回歸的判定基準，再以 GPU 加速相同分析；V2 不因導入 CUDA-X 而改變報告語意與測試規則。

02｜輸入資料規格與測試矩陣

Format1920 × 10801280 × 960640 × 360解碼／解析
RAW✓✓✓自建 Raw Reader（依像素格式與 Plane Layout）
H.264✓✓✓FFmpeg / PyAV
H.265✓✓✓FFmpeg / PyAV
MJPG✓✓✓JPEG Frame Parser 或 FFmpeg（視封裝）

必要檔案描述資訊

  • 所有檔案：格式、寬高、測試 ID、錄製情境、預期 FPS、對應的時間戳來源。
  • RAW：NV12 / I420 / YUYV / Bayer 等實際 Pixel Format、Bit Depth、Stride、Plane Offset、Packing、影格長度／標頭。
  • H.264 / H.265：Annex B 裸碼流或容器、PTS/DTS 是否存在、Codec Profile；裸碼流不能假定具有可驗證的擷取時間。
  • MJPG：連續 JPEG、AVI 或自訂封裝；需定義 Frame Boundary 與 Timestamp。

統一資料介面

FrameRecord:
  file_id: str
  frame_index: int
  pixels: ndarray | GPUBuffer
  pixel_format: str
  width: int
  height: int
  pts_ns: int | None
  capture_timestamp_ns: int | None
  decode_status: str
  metadata: dict

讀取器負責輸入差異，分析器只依賴標準化影格和 Metadata。CPU／GPU 實作透過 Backend 抽象切換。所有結果包含事件位置、原始計量值、閾值、檢測版本與判定信心。

判定狀態：PASS、FAIL、SUSPECT（人工複核）、UNVERIFIABLE（資料不足）、ERROR（解析失敗）。

04｜分析功能、方法與限制

模組分析方法輸出指標限制與檢核
FPS / Drop幀數、capture timestamp、連續影格間距、滑動視窗平均 FPS、最小局部 FPS、gap / drop 數無可信 timestamp 時不可宣稱實際 Capture FPS 達標
Freeze連續影格差、Hash、低運動區間與持續時間疑似凍結區段、秒數、畫面差異靜態場景可能誤報，建議移動物體／時鐘測試圖
Green / Ghost綠色 Mask、色度突變、區塊連通性、時序比對；移動殘影可用 Optical Flow異常像素比例、區域座標、事件影格植物或正常綠色物體易誤報；綠塊與殘影需分開判定
BlurLaplacian 變異數、參考圖／ROI；進階 Slanted Edge清晰度分數、低於基準事件不同解析度及場景不能共用任意閾值
ColorRGB/HSV/YCbCr 統計；標準色卡與色彩空間轉換後 ΔE00色偏、色塊誤差、白平衡偏差色彩準確度需要固定光源、參考色卡與正確轉換
DecodeFFmpeg 回傳碼、解碼紀錄、損毀幀／格式檢查解碼錯誤、損壞片段、解析度一致性解碼器不報錯不代表影像品質正常

FPS 驗證的必要前提

例如一個檔案有 300 Frames，若缺少實際錄製起迄時間或逐影格時間戳，只能確認幀數，不能確認錄製時真的是 30 FPS。裸 H.264/H.265 與 RAW 最應保留側錄 timestamp CSV；若只有容器 PTS，報告必須標註其來源與可信度。

測試模式

  • Generic：未知場景，輸出異常候選事件（SUSPECT）。
  • Reference：固定場景、色卡、解析度測試圖與 Golden Frame，可提供較嚴謹的 Pass / Fail。

05｜第一版 V1：Python + FFmpeg + OpenCV

V1 CPU Baseline｜先把判斷做對

技術選型

  • Python 3、FFmpeg / ffprobe：格式探測、H.264/H.265/MJPEG 解碼與錯誤紀錄。
  • OpenCV + NumPy：Frame Difference、Laplacian、色彩統計、ROI 和影像輸出。
  • PyAV（可選）：逐幀解碼與 Timestamp 訪問；RAW 使用自訂 Reader。
  • PyYAML、pytest、Jinja2：設定檔、回歸測試與 HTML 報告；JUnit XML 給 Jenkins。

V1 Deliverables

  1. CLI：videoqa analyze 單檔模式和 videoqa batch 12 組批次模式。
  2. 四種格式 Reader，驗證 Frame Count、寬高、解碼錯誤與有效影格。
  3. 六項檢測模組，附 profile / threshold 設定及事件擷取。
  4. HTML、JSON、CSV、JUnit 結果；問題影格及前後影格截圖。
  5. Golden Dataset、單元測試、整合測試和操作說明。

CLI 設計範例（預計實作）

videoqa batch --manifest dataset_001/manifest.yaml --output reports/run_001
videoqa analyze --input example.h265 --codec h265 --width 1920 --height 1080 --profile profiles/1080p.yaml

V1 結果與退出碼

建議 exit code：0 = 全部 PASS；1 = 至少一項 FAIL；2 = 輸入或工具執行錯誤。SUSPECT / UNVERIFIABLE 的 CI 政策應可設定，不可默默視為 PASS。

06｜第二版 V2：NVIDIA CUDA-X 加速影像分析

V2 GPU Acceleration｜沿用 V1 規則與輸出格式

技術選型與分工

環節GPU 技術候選導入策略
H.264 / H.265 解碼NVIDIA Video Codec SDK / NVDEC（屬 NVIDIA GPU 影片處理技術，非所有功能都在 CUDA-X 函式庫內）先確認 GPU、Codec、Profile、bit depth 支援，再量測
像素運算／色彩轉換CUDA-X NPP、CV-CUDA替換 CPU OpenCV 內高頻重複運算
差分、模糊、綠塊特徵CV-CUDA / NPP；必要時自訂 CUDA Kernel採用 GPU 批次處理，避免每幀不必要的 CPU↔GPU 傳輸
進階 AI 異常偵測（可選）TensorRT僅在有已標記的正常／異常資料集後評估，非 V2 必要前提
RAW / MJPEG 輸入CPU Reader 或其他相容解碼路徑 + GPU 分析不預設 NVDEC 直接支援所有 MJPEG 封裝或 RAW Bayer

支援環境與限制

  • 執行主機需具備相容 NVIDIA GPU、driver、CUDA runtime / toolkit 與配套函式庫。
  • 一般 RTX Ubuntu 工作站可做 POC；DGX Spark 屬 ARM64 / aarch64，必須確認 wheels、Docker image、CV-CUDA/NPP/解碼器的實際版本相容性。
  • V9 自研 SoC 若無 NVIDIA GPU，CUDA-X 應部署在外部測試工作站，不是直接移植到 V9。
  • V2 保持 CPU fallback：缺 GPU 或格式不支援時仍可執行 V1 分析。

V2 Deliverables

  1. GPU Capability Probe 和可切換的 --backend cpu|cuda|auto。
  2. GPU 加速核心運算、批次 pipeline、錯誤回退與相容性報告。
  3. CPU／GPU 一致性測試（浮點誤差容忍與相同事件判定）。
  4. Benchmark：每格式／解析度 throughput、總處理時間、GPU/CPU 使用率、記憶體及資料搬移成本。
  5. 容器化部署指引與 Jenkins GPU Agent 範例。

V2 是否成功的判斷

以 V1 為 baseline，先確保檢測結果一致，再以同一批 12 組檔案、相同硬體與執行條件比較總耗時、frames/s、p95 延遲（如適用）與資源成本。不預先承諾加速倍率；小檔案與資料搬移較多的工作可能不會比較快。

08｜驗收標準與風險管理

領域V1 驗收V2 驗收
讀取能力12 組指定輸入皆可解析，或精確指出格式資訊不足的原因同 V1，且 GPU 不支援時可安全回退
FPS有可信時間戳才做 Capture FPS Pass/Fail，否則 UNVERIFIABLE判定與 V1 一致
Freeze/品質正常與人工植入異常 Golden Dataset 可產生事件、指標與截圖在容忍誤差內與 V1 一致
報告HTML、JSON、CSV、JUnit、事件時間／Frame ID 可追溯格式相容，額外提供 GPU 指標
效能紀錄 CPU 基準處理時間、吞吐量與記憶體提供同條件 benchmark 與 GPU 加速收益／成本

主要風險與因應

  • 缺 Capture Timestamp：無法證明錄製時實際 FPS；優先修改錄製工具新增 sidecar metadata。
  • RAW 佈局未知：先完成 format contract，不用錯誤 stride 解碼後再做畫質判定。
  • 場景未知：Freeze、Blur、Green 的通用規則可能誤報；提供 SUSPECT 與固定圖卡／Golden Scene。
  • 色彩沒有標準：先輸出描述性統計，不宣稱色準合格；進階導入標準色卡與固定光源。
  • GPU 支援差異：事先測試驅動、CUDA、架構與解碼器支援；設計可回退的 CPU Backend。
  • GPU 與 CPU 浮點不同：比較檢測事件與容忍範圍，而不要求所有中間像素逐位元相同。

正式啟動前檢查清單

  • 取得 12 組代表性檔案（至少每種格式、解析度各一）
  • 確認 RAW layout / bit depth / stride / plane offset
  • 確認 MJPG 打包規格與 Frame Boundary
  • 確認 Capture Timestamp 可以取得或新增
  • 蒐集正常、凍結、綠塊、模糊、色偏樣本
  • 訂出 30 FPS 的容忍區間與穩定性要求
  • V2 確認 GPU 型號及環境相容性

09｜最終交付目標

V1：團隊可在沒有 NVIDIA GPU 的 Ubuntu/Linux 主機上，批次提交 12 種 V9 錄製檔案並取得可複核報告；工具的限制與無法判定項目清楚可見。

V2：不修改輸入資料規格與測試流程，即可透過 NVIDIA CUDA-X／GPU 影片處理能力加速部分檢測；保留 V1 為正確性對照和 fallback，並附加效能分析報告。

推薦優先順序：格式確認 → 統一 Reader → FPS/Freeze → 可追溯報告 → 綠影／色彩／模糊 → Golden Dataset → Jenkins → CUDA-X 加速。
